# 多人同屏打地鼠

## 题目目标
实现一个 5x5 的网格区域。系统每隔随机几秒钟，会在网格的随机位置刷出一枚“金币”。房间内的多个玩家看到后拼手速点击，谁先点到，谁就加 1 分。金币被点掉后立刻消失。支持多人在线对抗，重点要求实现严格的房间人数限制（最多5人）、完整的玩家加入/退出生命周期管理，以及绝对准确的并发计分逻辑。

## 核心页面
 - 房间大厅（输入房间号与昵称）。
 - 当首个玩家加入房间时，开启30秒准备倒计时。如果在30秒内房间达到满员（5人），则立即中断长倒计时，直接进入最后3秒的 3、2、1 开局倒计时；如果30秒结束仍未满员，则以当前房间人数直接进入3秒开局倒计时。
 - 游戏主视图（顶部倒计时 60 秒、左侧积分榜、中央 5x5 抢夺区）。

## 核心交互
 - 当房间已经到达最大玩家数量后，仍有玩家尝试加入时，接口需明确拒绝。如果没满，将玩家加入房间中，并向房间内广播“新玩家加入”。
 - 高频点击防抖/节流： 玩家在抢金币时往往会疯狂连续点击同一个位置。前端必须做节流或状态锁定，防止在 1 秒内向后端发送 10 次同样的“我点中啦”的请求。
 - 状态补偿（乐观更新与回滚）： 玩家点中金币时，前端可以先播放一个动画（比如金币播放碎裂、变灰、飞出特效）（乐观更新UI）。但是计分板的分数变化必须以服务端确认为准。这样既保证了点击的爽快感，又避免了分数反复横跳。
后端要求
 - 资源抢占与并发锁（核心重点）： 当 A 玩家和 B 玩家相差仅 10 毫秒同时点中了同一个金币，后端如何处理？使用数据库乐观锁、Redis 原子操作（如 SETNX）或内存级互斥锁，确保一枚金币绝对不可能给两个人同时加分。服务端针对“同一枚金币（具有唯一ID）”，前端在发出第一次请求后立即将其在本地标记为“锁定/已点击”状态，直到收到服务端的最终判定结果前，忽略对该金币的后续点击。
 - 定时器与主动推送： 后端需要有一个独立的游戏循环（Game Loop）定时器，负责随机生成金币坐标，并广播给房间内的所有人。
 - 心跳保活： 清理那些已经关掉浏览器但 WebSocket 没正常断开的“僵尸玩家”。

## 重点考察
 - 及格线： 知道并发会导致数据不一致，能说出一种锁的解决方案（即使代码写得不完美）。
 - 加分项： 
o了解网络延迟的必然性，能清晰表达出“前端展示的金币出现时间，和后端真实生成时间是有时间差的”，并给出合理的处理逻辑。
o在上述基础上拓展或完善项目
